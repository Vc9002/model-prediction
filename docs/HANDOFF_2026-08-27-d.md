## Task 2 (MLB NRFI) — artifact frozen and verified, deliberately NOT registered/promoted

Reproduced the shipped baseline via
`scripts/mlb_nrfi_half_inning_challenger.py`: holdout logloss **0.690572**
vs shipped reference 0.6910 (drift 0.000428, well inside the 0.002
reproduction tolerance). The incumbent (`MLBFirstInningModel`, base
`FEATURE_NAMES`, no umpire features) beats every challenger variant tested
— confirmed real, not fabricated.

Fit the same model (`src/model_prediction/models/mlb_first_inning.py`)
exactly as the challenger script does — probe split to find `train_end`,
freeze priors on the train window via `compute_first_inning_priors`,
rebuild the ledger with those priors, refit `MLBFirstInningModel().fit(train)`
on the 60% chronological split (4,020 games) — and froze its `to_dict()`
output into `config/models/mlb-nrfi-v1.json` with `model_version` set to
`mlb-nrfi-v1` and a correct `artifact_hash`
(`compute_artifact_hash`-compatible). Independently re-loaded the frozen
JSON via `MLBFirstInningModel.from_dict()` and re-scored the same 1,340-game
locked test split: reproduced **0.690572** exactly. All 19 coefficients,
scaler mean/scale, and intercept are real sklearn `LogisticRegression`
output — nothing hand-set.

**Deliberately did NOT add this to `config/production.yaml`'s `models:` /
`artifact_map:` / `champions:`, and did NOT remove it from
`blocked_workflows`.** Reason — a real landmine, not caution for its own
sake:

- `_forecast_mlb_nrfi_flat` in `src/model_prediction/cli/forecast.py`
  (~line 616) is the actual live NRFI serving path. It hardcodes
  `from ..models.mlb_nrfi import MLBNRFIModel; model = MLBNRFIModel()` —
  **the old, never-fitted, hand-set-weights model**
  (`src/model_prediction/models/mlb_nrfi.py`, intercept `0.0424`, weights
  like `-0.045` on FIP chosen by hand, not by regression). Its own
  module docstring in `mlb_first_inning.py` describes this old model's
  decomposed component as "systematically deflated" — it is not the
  ~0.6910 baseline.
- `MLBNRFIModel`'s default `model_version` parameter is **the literal
  string `"mlb-nrfi-v1"`** — the same model_id the new frozen artifact
  must use to match `_load_exact_artifact_contract`'s filename convention.
- `ProductionModelRegistry.champion()` falls back to the sole registered
  entry for a sport+market when no explicit `champions:` pointer exists
  (documented in `docs/HANDOFF_2026-08-27-c.md`'s Task 1 section, same
  quirk that made `promote()` refuse WNBA/MLB spread+total as "already
  serves"). If `mlb-nrfi-v1` had simply been added to `models:` as the only
  MLB/nrfi entry, `champion("MLB", "nrfi")` would resolve to it
  automatically — no explicit `champions:` edit needed to activate it.
- Put together: registering the artifact today would make
  `_is_registered_serving_model("mlb-nrfi-v1", "MLB", "nrfi")` return
  `True` — but the code path that actually runs still calls
  `MLBNRFIModel()`, the old deflated hand-set model, and stamps its picks
  with the same `model_version` string. The Main ledger would start
  receiving real, sized picks from the wrong, unvalidated model, labeled
  as if it were the artifact just validated at 0.690572 logloss. This is
  exactly the kind of silent-wrong-model bug the project's `CLAUDE.md`
  flags as the most damaging class in this codebase.

**What's actually needed before promotion is safe**: rewire
`_forecast_mlb_nrfi_flat` to load `mlb-nrfi-v1.json` via
`_load_exact_artifact_contract` and predict with
`MLBFirstInningModel.from_dict(artifact)` instead of `MLBNRFIModel()`. That
requires a **live** point-in-time feature builder for the model's 19
features (`away_starter_opp_1st_runs`, team home/away 1st-inning splits,
`park_1st_runs`, starter FIP/K%/BB%, `top3_composite`, starter days rest)
computed as of decision time for a *scheduled* (not yet played) game —
`build_first_inning_ledger` only exists as an offline batch walk-forward
builder over completed snapshots; there is no live equivalent yet. Building
one means replaying the same accumulator logic
(`starters`/`team_home`/`team_away`/`venues`/`batters`/`team_pool`/etc. in
`build_first_inning_ledger`) up to decision time and evaluating it once for
the upcoming matchup, resolving ESPN's probable-starter names to Stats API
player IDs. This is real new engineering in the project's most bug-prone
area (point-in-time correctness) — not a config change. Recommend scoping
it as its own phase with its own tests (train/serve parity, a live-feature
smoke test against a real recent game) rather than rushing it.

Until that wiring exists, leaving `mlb-nrfi-v1` in `blocked_workflows` and
out of `models:` is the *correct*, not merely cautious, state — it matches
current live behavior (NRFI stays research/paper-only) and avoids serving
the wrong model under a validated-sounding banner.
