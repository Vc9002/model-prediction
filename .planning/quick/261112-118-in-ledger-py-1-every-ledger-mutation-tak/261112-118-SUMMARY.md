# Quick Task 261112-118: Ledger lock hardening + deferred XLSX-rebuild documentation Summary

Added an in-process `threading.Lock` layer around `PickLedger._lock()` so
same-process threads (the daily job's `ThreadPoolExecutor` fan-out) serialize
through a fast in-memory primitive before ever touching the slower,
cross-process-safe fcntl file lock. Investigated the second half of the
originally-scoped work (the `rebuild_xlsx_projection` full-workbook-rebuild
cost) and determined, from live code, that it cannot be improved further
without changing an on-disk export contract two other files already assume
is exhaustive — documented as a deferred item rather than forced into a
risky change.

## What was built

### Task 1: Process-local lock for same-process ledger-mutation contention

In `src/model_prediction/ledger.py`:
- Added a module-level `_PROCESS_LOCAL_LOCKS_GUARD = threading.Lock()` and
  `_PROCESS_LOCAL_LOCKS: dict[Path, threading.Lock] = {}` registry,
  immediately after `_acquire_exclusive_lock`'s definition and before
  `LEDGER_SCHEMA_VERSION`.
- Added `_process_local_lock(path: Path) -> threading.Lock`, which resolves
  `path` to its canonical absolute form via `.resolve()`, then looks up (or
  creates) a `threading.Lock` for that resolved path under the guard lock —
  keying by resolved file path, not by `PickLedger` instance, so two
  `PickLedger` objects pointed at the same underlying file via different
  spellings of the path still serialize against the identical in-memory lock.
- Modified `PickLedger._lock()`: after the existing `retired` early-return
  and the `mkdir` call, it now acquires `_process_local_lock(self.lock_path)`
  with `timeout=LOCK_TIMEOUT_SECONDS` as a plain call (not `with`), raising
  `LedgerLockTimeout` naming `self.lock_path`/`LOCK_TIMEOUT_SECONDS` and
  stating "another thread in this process may be hung while holding it" on
  failure — mirroring but distinguishable from the existing cross-process
  message. The existing fcntl critical section (`lock_path.open("a+")`,
  `_acquire_exclusive_lock`, `yield`, `unlock`) is unchanged, now wrapped in
  an outer `try`/`finally` that releases the process-local lock.
  `_acquire_exclusive_lock`, `lock_exclusive`, and `unlock` themselves were
  not touched — cross-process behavior is byte-for-byte unchanged.

In `tests/test_ledger_hardening.py`, added two regression tests (placed
immediately after `test_audit_append_happens_while_the_ledger_lock_is_still_held`,
reusing its `request()`/`NOW`/`registry`/`ban_list` fixtures):
- `test_same_process_concurrent_appends_land_every_write_exactly_once` —
  16 concurrent `append_evaluated` calls on one `PickLedger` via an
  8-worker `ThreadPoolExecutor` produce 16 distinct `pick_id`s and
  `ledger.rows()` has exactly 16 rows afterward.
- `test_process_local_lock_is_keyed_by_resolved_path_not_ledger_instance` —
  two `PickLedger` instances pointed at the same file via different (but
  equivalent) paths resolve to the identical `_process_local_lock` object.

1:1 against every canonical row. Recommended next action: decide the split
policy (N-day cutoff, archive location, rebuild trigger), update both of
those files in the SAME change that introduces the split, then implement it.
