**Investigation findings baked into this plan (do not re-derive):**
- `PickLedger._lock()` (ledger.py, the `@contextmanager` right below
  `lock_exclusive()`) is used by EVERY mutating method (`initialize`,
  `_append_record`, `settle`, `void`, `update_closing`, `review_loss`,
  `score_research`, `remove_open_rows`/`supersede_open_rows`,
  `archive_settled_rows`, `import_rows`, `restore_unreplaced_picks`,
  `recompute_research_sizing`, `_set_legacy_units`, `rebuild_xlsx_projection`).
  It is never called re-entrantly on the same thread anywhere in the current
  codebase (every method that needs both `initialize()` and its own lock
  calls `self.initialize()` BEFORE its own separate `with self._lock():`
  block, never inside one), and the public `lock_exclusive()` wrapper has no
  callers anywhere in `src/` or `tests/` today — confirmed by grep. A plain
  (non-reentrant) `threading.Lock` is therefore safe to introduce.
- `src/model_prediction/cli/daily.py` fans out per-sport and per-market-type
  work through multiple `ThreadPoolExecutor` pools (forecast pool, flat
  re-log pool, a 16-worker research pool covering `mlb_totals`/`mlb_nrfi`/
  `soccer`/`tennis`/`cfb`/`wnba_spread`/`wnba_total`/etc., and settlement
  pools) — confirmed via grep (7 pools in that file). Tasks that share an
  underlying ledger path (e.g. two research tasks for the same sport) really
  do contend on the SAME `PickLedger._lock()` from different threads in the
  SAME process, which today only resolves via `_acquire_exclusive_lock`'s
  100ms-poll fcntl loop — correct, but built for cross-process safety, not
  speed.
- For item 2: `write_xlsx_rows_atomic` (`src/model_prediction/xlsx_ledger.py`)
  already carries the 2026-09-08 optimization (column-style caching, 4.36x
  speedup on a 1000-row/120-column workbook — `docs/PROJECT_OPTIMIZATION_2026-09-08.md`).
  There is no further free win inside the current "one workbook holds every
  canonical row" export contract — the write itself (temp file + rename) must
  serialize the complete row set every time by construction. The only real
  lever is splitting the export, and two things currently assume the single
  exported workbook is exhaustive: `tests/test_daily_cycle_smoke.py` (asserts
  `rebuild_xlsx_projection()` + `export_rows()` match `store.records(...)` via
  `compare(..., )["clean"] is True`) and `src/model_prediction/ledger_parity.py`
  (its production parity checker diffs `export_rows()` 1:1 against canonical
  records for every tier). Splitting the export without updating both would
  silently break parity checking. This is the exact "changes on-disk export
  semantics in a way that needs operator sign-off" case this task's own
  caution anticipated — scoped down to documentation, per that instruction.

  <action>
  In src/model_prediction/ledger.py, add a process-local lock registry
  immediately after `_acquire_exclusive_lock`'s definition — insert it right
  before the `LEDGER_SCHEMA_VERSION = "4"` assignment (after that function's
  final `time.sleep(LOCK_POLL_INTERVAL_SECONDS)` line and the two blank lines
  following it). Add a module-level `_PROCESS_LOCAL_LOCKS_GUARD = threading.Lock()`,
  a module-level `_PROCESS_LOCAL_LOCKS: dict[Path, threading.Lock] = {}`, and a
  `_process_local_lock(path: Path) -> threading.Lock` function that resolves
  `path` to its canonical absolute form via `.resolve()`, then under
  `_PROCESS_LOCAL_LOCKS_GUARD` looks up an existing lock for that resolved path
  or creates and stores a new `threading.Lock` if none exists yet, and returns
  it. Keying by the resolved path (not by `PickLedger` instance) means two
  `PickLedger` objects constructed against the same underlying file (e.g. via
  different relative paths) still serialize against the identical in-memory
  lock. `threading` is already imported at module scope — no new import needed.
  Add a short comment above the registry explaining why: same-process threads
  (the daily job's `ThreadPoolExecutor` fan-out) used to discover contention
  only via `_acquire_exclusive_lock`'s 100ms poll loop, which is correct but
  built for cross-process safety and far slower than an in-memory primitive
  for the common same-process case; serializing same-process callers through
  this lock first means at most one thread per process ever attempts the
  fcntl acquire at a time, so that acquire is normally uncontended, while the
  poll loop stays reserved for genuine cross-process contention (a second
  process — CLI re-run, dashboard, supervisor — holding the fcntl lock),
  which is exactly what `LOCK_TIMEOUT_SECONDS`/`LedgerLockTimeout` exist to
  diagnose.

  Then modify `PickLedger._lock()` (the `@contextmanager` method directly
  below `lock_exclusive()`). Keep the existing `if self.retired: yield; return`
  early branch and the `self.path.parent.mkdir(parents=True, exist_ok=True)`
  call exactly as they are. Immediately after that mkdir call: call
  `_process_local_lock(self.lock_path)` to get this ledger's in-process lock,
  then call `.acquire(timeout=LOCK_TIMEOUT_SECONDS)` on it explicitly (as a
  plain call, not via `with`, so a failed acquire raises before any `try`
  block opens). If `.acquire(...)` returns `False`, raise `LedgerLockTimeout`
  with a message naming `self.lock_path` and `LOCK_TIMEOUT_SECONDS` and
  stating "another thread in this process may be hung while holding it"
  (mirroring `_acquire_exclusive_lock`'s existing cross-process message, but
  naming the in-process case so the two failure modes are distinguishable by
  message text alone). On a successful acquire, wrap the EXISTING
  `with self.lock_path.open("a+") as lock: _acquire_exclusive_lock(...); try:
  yield; finally: unlock(lock.fileno())` block, unchanged, inside an outer
  `try` whose `finally` calls the process-local lock's `.release()`. Do not
  alter `_acquire_exclusive_lock`, `lock_exclusive`, or `unlock` themselves —
  this task only adds an outer in-process serialization layer around the
  existing fcntl critical section; cross-process behavior (including the
  existing `LedgerLockTimeout` diagnostic for a hung cross-process holder)
  must be byte-for-byte unchanged.

  Add two new tests to tests/test_ledger_hardening.py, placed near
  `test_audit_append_happens_while_the_ledger_lock_is_still_held` (reuse that
  test's exact fixture/helper pattern: the module's `request()` helper, `NOW`
  constant, and the `registry`/`ban_list` pytest fixtures already used there
  — do not redefine them). First, a concurrency-correctness test: construct
  ONE `PickLedger` against a `tmp_path` workbook, use
  `concurrent.futures.ThreadPoolExecutor(max_workers=8)` to call
  `ledger.append_evaluated(...)` 16 times concurrently (each call built from
  `request(f"concurrent-{index}")` and `evaluate_eligibility(req, registry,
  ban_list, Exposure(), UnitPolicy(), NOW)` for a distinct `index` in
  `range(16)`), collect the 16 returned rows, assert their `pick_id` values
  are all distinct (16 unique ids, no `DuplicatePickError` raised), and
  assert `ledger.rows()` has exactly 16 rows afterward — proving same-process
  concurrent mutation on one ledger path still lands every write exactly once
  under the new lock. Second, a unit test importing `_process_local_lock`
  directly from `model_prediction.ledger`: construct two `PickLedger`
  instances pointed at the same underlying xlsx path (one via `tmp_path /
  "picks.xlsx"`, one via a second, differently-spelled but equivalent path to
  the same file) with different audit paths, and assert
  `_process_local_lock(ledger_a.lock_path) is _process_local_lock(ledger_b.lock_path)`
  — proving the dedup key is the resolved file path, not the `PickLedger`
  instance, so the fast path actually protects cross-thread access to the
  same file rather than silently granting two independent locks.
