<objective>
Tighten `_lookup_model_prob` in `src/model_prediction/portfolio/polymarket_scanner.py` so a Main/Flat pick can only supply `p_model` for a Polymarket market when the pick is for the exact same real-world UTC calendar date as that market -- not an unbounded "same two teams, any date" fallback. This is the deferred item from quick task 261112-01r's audit (docs/ROADMAP.md item 5), and the operator chose to investigate and fix it now rather than leave it open.

Planning already ran the live-data investigation this task's instructions required (read-only, against the repo's real `data/odds/**/*polymarket_snapshots.jsonl` corpus -- 697 files, 696,839 lines -- and the real Main+Flat picks index, 22,605 rows, via the project's own `_get_logged_picks`/`_normalize_league`/`_team_matches` helpers). Findings the executor should treat as settled (re-deriving them is not required, but spot-checking is welcome):

- Of 6,037 markets that matched a Main/Flat pick on league+market_type+team-pair, the current unbounded fallback lets 1,187 of them (~19.7%) be priced by a pick whose raw `event_start_utc[:10]` date differs from the market's.
- Those date gaps range from 1 day to 113+ days, and every single one, once inspected directly (printed with full timestamps, not just dates), is a genuinely different real-world event -- a different NBA game, a different esports best-of in a tournament the same two teams play again weeks or months later, etc. There is no case where a real single game legitimately needs a multi-day tolerance window. The existing `_lookup_model_prob` already includes a secondary tie-break on `created_at_utc`, so when a same-date pick AND a stale cross-date pick both exist, the +10 same-date score bonus already makes the same-date one win -- the bug only actually fires (produces a wrong answer) in the 1,187 cases where no same-date candidate exists at all, and the code falls back to the most-recently-created cross-date pick instead of returning no match.
- Critically, 117 of those apparent 1,187 "cross-date" cases are NOT genuinely cross-date -- they are the real version of the "legitimate same-day, crossing a UTC boundary" case this task was explicitly warned to check for. Main/Flat ledger rows don't consistently normalize `event_start_utc` to `Z`/UTC notation; some store the original local-offset string (e.g. `2026-10-19T20:00:00-0400`), which is the exact same instant as a market's `2026-10-20T00:00:00Z` -- same real UTC calendar date -- but a raw `[:10]` substring slice reads them as different days ("2026-10-19" vs "2026-10-20"). Fixing this requires parsing both timestamps with `datetime.fromisoformat` and comparing their actual UTC calendar date, not adding a multi-day tolerance window. After doing that normalization correctly, the genuinely-different-event count is 1,070 of 6,037 (~17.7%), and the same-date-available count rises from 4,850 to 4,967.
- 0 of the 85,554 real moneyline/nrfi/yrfi snapshot lines inspected have a missing/empty `event_start_utc`, and 0 of the 22,605 real Main/Flat picks have a missing, unparsable, or naive (no tzinfo) `event_start_utc`. The fail-closed paths this fix adds for those cases are real safety nets, not something that fires on live data today.

Decision this plan implements: require an EXACT same UTC calendar date (zero-day tolerance), computed via proper ISO-8601 parsing and UTC conversion -- not a raw string slice, and not a multi-day tolerance window (the investigation found no legitimate case for one).

Tracer-first decomposition does not apply: this plan tightens one existing matching function, adds regression tests, and updates one doc paragraph. It builds no new layered capability.

Purpose: stop the daily Polymarket edge scanner (cli/daily.py step 10, `polymarket_edge.scanner_enabled: true`, production call is `require_model=True`) from recording a paper-trading pick priced off a stale or wrong-fixture Main/Flat forecast, per the project's point-in-time correctness invariant.
Output: one tightened matching function, three new regression tests (two of them red before the fix), and a closed-out ROADMAP item.
</objective>
