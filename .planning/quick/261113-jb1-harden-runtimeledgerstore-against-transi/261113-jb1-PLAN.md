# Harden RuntimeLedgerStore against transient sqlite "disk I/O error" under host memory pressure

## Evidence (root cause)

- `daily-20261113T053001Z-8f176c` exited 1: the NCAAB forecast raised
  `sqlite3.OperationalError: disk I/O error` inside `RuntimeLedgerStore.records()` while
  `PickLedger._append_record` re-read the Flat mirror. The run then failed `ledger_coverage`.
- Windows System log, Resource-Exhaustion-Detector Id 2004 ("low virtual memory condition") at
  00:41:49 and 00:42:24 local on 2026-11-13, inside that run's Step 2 window (05:33Z to 05:49Z).
  Top consumers: Overwatch.exe 3.6 to 4.9 GB, the daily python.exe 3.4 GB. DWM crashed at 00:41:53.
  The 2026-11-12 05:30Z failure window carries the same 2004 events.
- Drive E: healthy NVMe, `PRAGMA quick_check` ok, no disk/NTFS events, no Defender scan, the
  offsite backup runs at 08:00Z, and `log_maintenance` only VACUUMs top-level `*.db`, so none of
  those explain it.
- The store opens one connection per forecast thread (16 workers) with `mmap_size=256MB` and a
  64 MB page cache each. Memory-mapped reads under a commit-limit squeeze surface as
  `SQLITE_IOERR` ("disk I/O error"), not `SQLITE_NOMEM`.

## Tasks

1. `src/model_prediction/runtime_ledger_store.py`: set `PRAGMA mmap_size=0` and
   `cache_size=-32000`; add `_reset_connection()`; wrap the read in `records()` with a bounded
   retry (3 attempts, 0.5s/1.5s/3.0s backoff via a module-level `_RETRY_DELAYS`) that resets the
   thread's connection on `OperationalError` whose message contains "disk I/O error" or
   "database is locked", re-raising after the last attempt. Comments explain the why.
2. `tests/test_runtime_ledger_store.py`: regression tests — connection pragmas report mmap 0 and
   cache -32000; `records()` survives two transient disk I/O errors (fault-injected execute),
   reconnects, and returns rows; a persistent error still raises after the bounded attempts.
   Verify the retry test fails against the pre-fix code before landing the fix.
3. `docs/DEBUG.md`: entry with the trace, the 2004 events, and the fix.

Verification: `pytest tests/test_runtime_ledger_store.py -o addopts='' -q`, `ruff check src/ tests/`.
Then rerun the full daily forecast through `run_supervisor run daily` (operator request).

Not in scope: the machine-level memory pressure (games, rust-analyzer) and the per-append
full-mirror re-read in `PickLedger._append_record`, which is the real reason the daily run holds
so many large result sets at once; recorded in the DEBUG entry as the follow-up.
