<objective>
Generalizes the 2026-10-26 events.jsonl fix (audit.py's append() switched from a full-file read under lock to a tail-only backward read) by auditing every other JSONL/log reader in the ledger-adjacent path for the same two anti-patterns -- holding a lock during a full-file read, or an unbounded full scan where a tail-read/indexed lookup would do -- and fixing the genuine instances found.

Live-code investigation (this session) found:
- CONFIRMED CORRECT, NOT TOUCHED: system_health.py's `_latest_event_utc` does a full max-scan over `data/historical/{sport}_games_all.jsonl` -- verified live: the file is genuinely ingest-ordered (the docstring and the code agree: late-arriving historical backfills land at the end of the file long after newer events), so a tail-read would silently return a wrong, stale timestamp. No lock is involved. This is the pattern already documented in CLAUDE.md -- left alone.
- CONFIRMED CORRECT, NOT TOUCHED: `data_sources/mlb_lineups.py::LineupStore.merge()` and `data_sources/mlb_statsapi.py::MLBGameSnapshotStore.merge()` both read the whole file under an exclusive lock, but each is a genuine read-modify-write: a re-observed lineup/snapshot must be folded into its existing row by content hash / game_pk, which requires every existing row, not just the tail. Architecturally different from audit.py's old bug, where only the single last event's hash was ever needed. Not touched.
- CONFIRMED CORRECT, NOT TOUCHED: `run_supervisor.py` and `ledger.py`'s `_lock()` guard SQLite operations and lease files, not a JSONL full-file read. `bans.py` locks a small YAML governance config for its own read-modify-write, not an append-only growth log. Not touched.
- GENUINE ANTI-PATTERN, FIXED HERE: `dashboard/orders.py::_audit_tail()` reads the entire `events.jsonl` into a Python list of lines, then slices the last 25, purely to serve the dashboard's `/api/audit` route. A live copy of `data/events.jsonl` on disk at planning time is 428MB across 241,991 lines -- this function pays for all of it on every cache-miss dashboard poll (cached 60s) just to show the newest 25 events.
- GENUINE ANTI-PATTERN, FIXED HERE: `data_sources/polymarket_execute.py`'s single_order policy check (inside `PolymarketExecutor.execute`, real-money buy gate) calls `reversed(self.audit.events())` -- `events()` parses every line in `audit.jsonl` into a list before the caller ever sees one event, and the common case (a pick_id with no prior buy -- i.e. every first-time buy) scans the entire thing with no early exit, on a path that exists specifically to prevent a double real-money order.

Both fixed call sites share one root cause -- `AuditLog.events()`'s eager, unbounded, fully-materializing read -- so the fix adds one new primitive to `audit.py` (the same file the original bug lived in) and rewires both consumers to it, rather than patching each call site with a bespoke, ad hoc read.

Purpose: stop two real, currently-live full-file reads of an append-only, unboundedly-growing audit log -- one on a dashboard endpoint that is polled repeatedly, one on the gate that stops a second real-money order from firing against the same pick.

Output: `AuditLog.reversed_events()` in audit.py with four new regression tests in tests/test_audit.py; `_audit_tail()` and the single_order policy check rewired to it; one new regression test in tests/test_dashboard_server.py; the three pre-existing single_order policy tests in tests/test_execution_gate.py passing unchanged, proving behavior was preserved.

Add a new method `reversed_events(self) -> Iterator[dict[str, Any]]` to `AuditLog` in `src/model_prediction/audit.py`, placed directly after the existing `events()` method (after line 65) and before `append()`. It must yield parsed events newest-first while never loading or parsing the whole file before the caller sees the first one -- the defining difference from `events()`, which parses every line up front. Implement it as a standalone generator, independent of `append()`'s own tail-read: do not refactor, call into, or otherwise touch `append()`'s existing backward-chunk logic for the hash-chain previous-hash lookup (lines 76-100) -- that code is already fixed and tested, and this plan's blast radius must not include it.

Algorithm (open the file in binary mode; if it does not exist or is empty, return with no items yielded): seek to the end, then read backward in 65536-byte chunks -- the same chunk size `append()` already uses -- prepending each newly-read chunk's bytes in front of a running byte buffer. After each chunk read, split the current buffer on newline bytes. If the current seek position has reached 0 (start of file), every resulting segment is a complete line -- consume the entire buffer. Otherwise, once there is more than one segment, the first segment may still be an incomplete line continuing into data further back that has not been read yet, so keep only that first segment as the carry-forward buffer for the next backward read, and treat every segment after it as complete. While there is only a single segment and the start of the file has not yet been reached, keep reading backward without yielding anything. Whenever a batch of complete line segments is identified this way, iterate that batch in reverse (the last line physically in the batch is the most recently appended), strip whitespace, skip any blank segment, and `json.loads` the rest, yielding the parsed dict. A segment that fails to parse as JSON is skipped via `continue`, not raised -- both call sites wired in Task 2 already tolerate a corrupted record rather than crash a dashboard poll or a real-money gate, and `reversed_events()` should carry that same tolerance so neither caller needs its own try/except around the generator.
