Phase 2 item 2 of the ledger-improvement plan (`C:\Users\Vince\.claude\plans\golden-whistling-haven.md`, quick task 261112-111): decide whether `data/model_ledgers/*.xlsx` (written by `model_ledger.py`'s `ModelLedger`, one workbook per model identity) should become a generated-on-demand report instead of an independently-written projection that can drift, and apply a minimal safe fix.

**Planning-time verdict, from live code and live data: full conversion is NOT a quick-task-safe change, and this plan does not attempt it.** `ModelLedger` is not a disposable export like the per-sport Main/Flat xlsx (`rebuild_xlsx_projection`, which fully regenerates from canonical SQLite on every write). It is an independently mutable evidentiary store: `append_prediction`/`settle`/`settle_event`/`record_operator_decision` in `model_ledger.py` each do their own read-modify-write cycle under their own file lock, called as fail-soft side-effect hooks from three places in `ledger.py` (`_append_record` ~:972-980, `settle` ~:1370-1378, `update_closing_data` ~:1888-1896) -- "additive... never instead of" the real PickLedger write, by a 2026-08-02 operator directive quoted verbatim in `model_ledger.py`'s own module docstring. Its `OPERATOR_FIELDS` block and several `MODEL_FIELDS` (`code_revision`, `model_uncertainty`, `input_availability`, `missing_inputs`, `source_lineage`) have **no column in canonical `ledger_records`** (confirmed by reading `runtime_ledger_store.py`'s `_SCHEMA`) -- a pure "generate from SQLite on demand" conversion would silently drop exactly the data that directive asked to keep. That is a missing-information constraint, not a difficulty judgment: converting for real would mean first designing a new persistent home for those fields, which is its own deliberate operator decision, not a default to invent inside a quick task.

**What actually causes the drift** this plan's description names (cs2-tiered-elo 22-row backlog, 6 identity conflicts): every one of the three call sites above wraps its `model_ledger` hook in `try: ... except Exception: logging.getLogger(__name__).warning(...)`, with no retry and no alerting beyond a log line. A failed write (a lock timeout under the daily job's per-sport `ThreadPoolExecutor` fan-out -- `model_ledger.py` has its own independent OS-level lock with no in-process fast path, the same contention shape sibling quick task 261112-118 is currently fixing for `ledger.py`'s own lock, just not here) silently strands or skips a row while the real, canonical write already succeeded. Live evidence gathered at planning time (read directly via `ModelLedger`, not the broken audit script -- see below): **4,133 total open rows across the 31 live, non-backup `data/model_ledgers/*.xlsx` workbooks**, with the oldest dating back to 2026-08-29/08-30 (`cs2-tiered-elo.xlsx`: 1,111 open, oldest 2026-08-30; `ncaaf-spread-baseline.xlsx`: 580 open, oldest 2026-09-04; `ncaaf-total-baseline.xlsx`: 589 open, oldest 2026-09-04) -- today is 2026-11-12, so those events have almost certainly already completed and settled in canonical `ledgers.db` long ago. Full per-model counts are recorded in the context section below; re-measure at execution time since the daily job writes 4x/day.

**The minimal, safe fix this plan ships:** `audit_ledger_pnl.py`'s existing dry run (its default, non-mutating mode) *already computes* this exact drift signal into its JSON report -- `model_repairs_planned_total` (stranded-open rows with an unambiguous canonical-backed settlement available) and `model_settlement_conflicts` (rows disagreeing on economics, which the script's own docstring says are "never auto-resolved"). But its exit code ignores both fields entirely, so a dry run can report real drift and still exit 0 -- exactly why this needed one-off manual repair scripts to even get noticed. Task 1 makes the exit code (and a printed stderr summary) reflect that signal, with zero changes to the write path, the apply/repair logic, or any ledger. Task 2 records the full investigation and verdict in `docs/LEDGER_ROUTING.md`, including the follow-ups this plan deliberately leaves open.
