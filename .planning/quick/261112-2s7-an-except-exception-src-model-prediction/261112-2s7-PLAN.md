**Planning-time verdict, from live code and live data: the asymmetry is REAL but only PARTIAL -- fixing it alone would not have stopped the dominant leak mechanism.**

Direct code read confirms the asymmetry exactly as flagged: `xlsx_ledger.py` (:133) catches `except Exception:` around its cleanup-and-reraise block (`if os.path.exists(temporary): os.unlink(temporary)` then `raise`); `model_ledger.py`'s `_write_predictions_atomic` (:741) catches `except BaseException:` around the equivalent block. `KeyboardInterrupt` and `SystemExit` are `BaseException` subclasses that are NOT `Exception` subclasses -- if either is raised between `workbook.save(temporary)` and `_replace_with_retry` inside `write_xlsx_rows_atomic`, the narrower clause skips the `os.unlink` and the temp file leaks. This is a real, confirmed bug.

**But it is not the whole story.** This project's scheduled jobs (`run_supervisor.py`) kill a worker that exceeds its timeout with `taskkill /F /T /PID` on Windows (:341-345) or `proc.kill()` on Unix (:347) -- both a hard, uncatchable process termination (the Unix path sends SIGKILL). A hard kill runs NO Python code at all: no `except Exception`, no `except BaseException`, no `finally` -- nothing. If the kill lands while `write_xlsx_rows_atomic` or `_write_predictions_atomic` is mid-`workbook.save`, BOTH functions leak today, and no except-clause change, however wide, can ever fix that. `DEFAULT_WORKER_TIMEOUTS` (run_supervisor.py :101-110) tops out at 3600s for `daily`/`rebuild-shadow`; `PickLedger._write_rows` (ledger.py :2185ish) calls `write_xlsx_rows_atomic` as a best-effort export on every ledger commit under sqlite authority (the project default since 2026-08-16), so there is real exposure to this window on every scheduled run.

Live evidence gathered at planning time supports the hard-kill explanation being the dominant one, not the except-clause asymmetry alone: a SECOND real orphaned temp file was found during this investigation's own code read, `data/sports/cs2/picks-39cd77nx.xlsx` (3772 bytes, confirmed `zipfile.BadZipFile` -- not a valid xlsx, gitignored stray debris, same `picks-*.xlsx` naming shape as the previously-removed `data/main/picks-js40dfcf.xlsx`, which was 3770 bytes). Both are tiny fragments of what a real workbook save produces (the real sibling workbooks in the same directories are 300KB-1.5MB) -- consistent with `workbook.save` being interrupted very early, which a hard kill explains just as well as a `KeyboardInterrupt` would, and this codebase's scheduled, non-interactive daily/production/rebuild-shadow jobs (run headless via `subprocess.Popen` with `CREATE_NO_WINDOW` on Windows) have essentially no path to a `KeyboardInterrupt`/`SystemExit` at all -- those only arise from an interactive Ctrl-C or an explicit `sys.exit()`, neither of which fits a backgrounded scheduled job.

**The fix this plan ships, addressing both the confirmed bug and the dominant mechanism it doesn't cover:**
1. Widen `xlsx_ledger.py`'s `except Exception` to `except BaseException` to match `model_ledger.py`, closing the real, confirmed gap for the in-process-catchable case (e.g. a manual Ctrl-C during an ad hoc interactive run of a CLI command).
2. Add a shared, age-gated `_sweep_orphaned_temp_files` helper, called at the start of BOTH `write_xlsx_rows_atomic` and `_write_predictions_atomic`, each sweeping its own directory for its own temp-file naming pattern before starting a new write. This is what actually makes the dominant hard-kill case self-healing -- the crash itself can never be caught, but the NEXT normal write to that same destination now cleans up what the crash left behind, rather than letting it accumulate indefinitely (which is exactly what let `data/main/picks-js40dfcf.xlsx` sit for ten days and crash `audit_ledger_pnl.py`'s tier scan).
3. Remove the second confirmed-corrupt orphan found during this investigation (`data/sports/cs2/picks-39cd77nx.xlsx`).
4. Record the real investigation conclusion in `docs/LEDGER_ROUTING.md` -- the asymmetry was real but partial, not the single root cause -- closing out 261112-111's open follow-up honestly.
